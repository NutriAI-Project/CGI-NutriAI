NutriAI on AWS EKS — traffic, GitOps & secrets flow

How a request reaches a pod, how images and config get there via GitOps, and where IAM/RBAC and secrets sit along the way. Reflects CGI-NutriAI plus the optional alb-ingress/ and istio-service-mesh/ additions — neither applied by default.

request / data path GitOps · IAM · control-plane optional Istio mesh path (separate stack)

Entry points

One shared ALB (nutriai-alb) host-routes app.* to kgateway and argocd.* to ArgoCD — one bill, two apps. The optional mesh demo gets its own ALB (nutriai-mesh-alb), kept separate on purpose.

Why two subnet tiers

Public subnets hold only the ALB's ENIs, the NAT Gateways, and the bastion — nothing that runs application code. Every pod, including the EKS worker nodes themselves, lives in the private subnets and reaches the internet only outbound, through NAT.

Secrets never touch git

External Secrets Operator assumes an IRSA role to read nutriai/prod/<service> from Secrets Manager and materializes it as a native Secret — the value is never committed, never in a Helm value file.

Two layers of RBAC

Kubernetes RBAC scopes who can change what (ArgoCD's AppProject, the mesh-editor Role). Istio's AuthorizationPolicy scopes which workload can call which workload — independent controls, both shown.
